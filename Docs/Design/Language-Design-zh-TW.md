# @Doc 語言設計 — 為什麼需要一個 Semantic Document IR

*[English version](./Language-Design.md)*

> 本文件不談節點層級的語法(`@bold`、`@table`、`@meta` 等,詳見 [Block Syntax Specification](../../Block-Syntax-Specification.md) 與 [Inline Syntax Specification](../../Inline-Syntax-Specification.md))。它回答一個更根本的問題:Markdown、HTML、JSON、XML 都已經是成熟的「文件標記」方案了,為什麼還需要 @Doc?簡短的答案是:它們沒有一個是為「AI 生成來源、程式解析、多重渲染」這條三段式管線設計的——而且每一種都在管線的不同環節上失守。

## 1. 管線的轉變

過去的文件格式,都是為了單一作者、單一消費路徑而設計:

```text
Human
  ↓
Document
  ↓
Renderer
```

作者是人類,文件只需要被另一個人閱讀,或被單一渲染器轉換成 HTML、PDF 等最終輸出。

AI 的出現改變了這條管線。今天,一份文件更常經歷的是:

```text
AI
  ↓
Semantic Document
  ↓
Parser
  ↓
AST
  ↓
Renderer Adapter
  ↓
HTML / PDF / Native App / Search Index / Another AI
```

文件不再只是「給人看的文字」。它已經成為 AI、Parser 與 Renderer 之間共同交換的**中介表示(Intermediate Representation)**。一個為上一條管線設計的格式,不會自動適用於這條新管線——而下面每一種格式,都是為第一條管線設計的。

這代表 AI 時代的文件格式,必須同時滿足三個階段的需求,而不是只服務其中一端。

## 2. 為什麼不是 Markdown

Markdown 的設計目標,是讓人類能用純文字輕鬆閱讀與撰寫。正是這個設計目標,讓它具備了一種「機器生成端」承受不起的寬容度。

LLM 讀 Markdown 沒有任何問題。問題出在**生成**端:讓一個模型生成 Markdown 交給下游程式解析,輸出的結構幾乎無法被可靠保證——縮排敏感的巢狀結構、清單項目漂移、表格損壞、parser 方言差異,都是有文獻紀錄的失敗模式。而 CommonMark 的形式化規格,是在這個格式誕生數十年後才出現的補丁,修補的是一套原本從未打算被確定性解析的語法。

更深層的問題是:Markdown 不承載語義意圖。它能表達「這段文字是粗體」,卻無法表達「這個按鈕是 primary 變體」或「這個表格需要斑馬紋樣式」。任何想加入領域語義的嘗試,都被迫依賴臨時的擴充機制——frontmatter、自訂容器、內嵌 HTML——沒有一個是標準化的,全部都是格式本身的逃逸口。

對生成式管線來說最致命的是:Markdown 的結構錯誤很少產生「解析錯誤」,它產生的是**悄悄變成另一種解析結果**——清單多縮排一層、段落與上一段合併——沒有任何訊號顯示出了問題。這正是機器生成目標最無法承受的失敗模式。

---

## 3. 為什麼不是 HTML

HTML 幾乎能表達任何東西,代價是把結構、展示、行為這三個各自獨立的關注點,壓縮進同一份產物裡。它是一個**渲染目標**,不是一個**書寫記法**:它編碼的是「如何畫出一個矩形」,而不是「這個矩形代表什麼」。

對 AI 生成而言,HTML 有兩項具體成本。第一,每個元素都需要成對的閉合標籤,這既消耗 token,也是模型最容易漏寫或寫錯的地方——一旦出錯,渲染結果就無法恢復。第二,HTML 沒有封閉的詞彙表——一個幻覺出來的標籤名(`<fancybutton>`)不會是語法錯誤,瀏覽器只會把它當成未知元素默默忽略或錯誤渲染。沒有任何 schema 層級的機制,能像封閉文法那樣捕捉一個憑空捏造的節點。

因為展示邏輯已經寫死在結構裡,同一份內容要換一個平台呈現——列印、原生 App、或另一個要回頭讀取它的 AI——通常意味著重寫標記本身,而不只是換一個渲染器。

---

## 4. 為什麼不是 JSON

JSON 解決的是資料交換,不是文件。它沒有「文字流」這個原生概念——文件最基本的單位,一句話中間夾著一個行內強調,JSON 完全沒有直接的表達方式。每一個試圖把富文本塞進 JSON 的工具,都各自重新發明了一套 runs/spans schema(Slate、ProseMirror、Notion API、Contentful 的 Rich Text 欄位)——而這些 schema 從未收斂成一個標準,因為 JSON 是「鍵值形狀」,不是「文字流形狀」。

對 AI 生成來說還有兩個更具體的問題:

- **沒有局部有效性。** 少一個逗號或括號,整份文件全部作廢。一個以文字為基礎的文法,即使某處寫錯,通常還能被辨識或優雅降級——JSON 完全沒有這種局部容錯的空間。
- **Token 成本。** 巢狀的 JSON 在每一層都要重複結構性的 key(`"type"`、`"children"`、`"props"` ……)。同樣的語義內容,用一個緊湊的記法表達,往往只需要一小部分的 token。

JSON 在它被設計的目的上——結構化資料交換——表現得很好,但文件的本質是「以文字為主、結構疊加其上」,而不是「結構為主、文字塞進葉節點」,這正是 JSON 的弱項。

---

## 5. 為什麼不是 XML

XML 在結構嚴謹性上比 Markdown 或 JSON 都更完整——DocBook、XHTML 都證明了它能表達複雜文件——但這份嚴謹是用**雙倍 token 成本**換來的:每個節點都是開合標籤成對出現,還要處理屬性引號跳脫與實體跳脫(`&amp;`、`&lt;`)。對一個在驗證型編輯器裡「寫一次」的人類作者而言,這個成本幾乎無感;但對一個每輪對話都要重新生成內容的模型而言,這是實實在在、不斷累加的開銷,而且它同時打開了兩個各自獨立的失敗面——一個未閉合的標籤,和一個寫壞的屬性,任何一個都能單獨弄壞整份文件。

XML 也沒有解決「哪個子元素是內容、哪個是中繼資料」這個問題——這個區分完全活在外部 schema(DTD/XSD)裡,而不是文法本身。讀者(人類、parser、或模型)必須先知道 schema,才能判斷哪個巢狀元素是「重點」、哪個只是記帳用的屬性。這正是 @Doc 用全域唯一含義的 `[]` 內容槽位想要根除的歧義——XML 從未把它當作一級設計問題處理過。

## 6. 三個階段,三種需求

**生成(Generation)**需要:

- 封閉且穩定的節點詞彙表。
- 單一且無歧義的「這是內容」表示法——絕不依賴上下文推斷。
- 局部容錯——一個節點寫壞,不該讓整份文件失效,不像 JSON 那樣要嘛全對要嘛全錯。
- 低 token 成本——生成成本與延遲都隨輸出 token 數線性增加,更緊湊的記法在規模化之後就是純粹的省錢。

**解析(Parsing)**需要形式化、無歧義的文法。Parser 不能靠「大概知道作者的意思」工作——同一份輸入,必須永遠得到同一棵 AST。Markdown 的縮排與巢狀規則高度依賴位置與上下文;CommonMark 事後補上了*部分*形式規格,但本質上仍是在修補一套原本並非為確定性解析而設計的語法。

**渲染(Rendering)**只該決定「如何呈現」,不該決定「這代表什麼」。同一棵 AST 應該能在不修改任何來源內容的情況下,編譯為 Tailwind HTML、Inline Style HTML、React 元件樹、PDF、DOCX、搜尋索引、RAG metadata,或任何尚未出現的渲染目標。這要求格式描述的是**語義**,而不是**展示**——恰好與 HTML 與生俱來的結構相反。

## 7. 編譯器的觀點

這其實是一個經典的編譯器問題,套用到文件上:**前端**(作者或 AI 所寫的內容)不應該與**後端**(渲染結果)耦合。

上面每一種格式,都在某個環節打破了這條邊界:

- Markdown 把語義壓縮成排版符號。
- HTML 把語義與展示焊死在同一份產物裡。
- JSON 把文件流退化成任意的資料形狀。
- XML 同時保留了兩者,但以大量冗餘語法作為代價。

每一種格式,都壓扁了一個文件即中介表示(document-as-IR)必須保留完整的區分。

---

## 8. Semantic Document IR

@Doc 的假設是:**文件首先是一棵語義樹,其次才是一份可閱讀的文字。**

因此,它提供一個固定且形式化的文法,而不是一套有機生長出來的慣例:

```text
@node(modifier){styles}[content]<action>
```

其中每個槽位只有唯一語義,且這個語義不因上下文而改變。(尾綴的 `<action>` 槽位是長期目標,不是現行文法——目前實際支援的範圍見 [README § 核心語法](../../README.md#核心語法--core-syntax) 的但書。)

@Doc 不是 Markdown 的替代品,也不是 HTML 的簡寫。它位於三種讀者之間——生成它的 AI、解析它的 Parser、繪製它的 Renderer——作為上述所有格式都未曾被設計來扮演的中介表示。

---

## 9. 設計原則

```text
Semantic First, Layout Later
```

上面沒有一種格式是「設計失敗」的。每一種都為它服務的讀者做了最佳化——Markdown 為寫散文的人類,HTML 為畫像素的瀏覽器,JSON 為兩個交換資料的程式,XML 為需要驗證的文件樹。@Doc 的設計目標不同:管線裡沒有任何一方——人類、AI、或編譯器——需要為了遷就另一方的限制,扭曲自己對這份文件的模型。
